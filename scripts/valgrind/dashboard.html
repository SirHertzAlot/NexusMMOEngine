Memcheck: memory errors
Reports from valgrind-out/memcheck. Drop XML files anywhere to add more.

      
 

    

    
How to read this
      
Memcheck runs each addon's tests under Valgrind and reports memory mistakes. Each card below is one test run (one addon); the number is how many distinct errors it found.

      
    
        
  • Leak_DefinitelyLost: memory was allocated and nothing points to it any more, so it can never be freed. Small leaks (tens of bytes) at startup are usually harmless; a leak inside a function that is called repeatedly grows without limit.
    • 
        
  • UninitCondition: a branch depended on a value that was never set. Real bugs do this, but so does Node's own JIT compiler, so check who is in the stack.
    • 
        
  • ENGINE: the code at fault is ours. The first frame after the allocator is in one of our addons (*.node). Same rule as npm run valgrind:memcheck, and the only class that fails valgrind:check.
    • 
        
  • VIA ENGINE: our code is on the stack but the fault is inside Node or V8, for example a native object that was never finalised at exit. Often harmless, but it is our allocation, so read it.
    • 
        
  • RUNTIME: Node, V8 or libc only. It appears in every run whatever the engine does. Nothing is suppressed or hidden, since it is part of what the engine costs; it just doesn't gate.
    • 
        
  • Hotspots group errors by where they start, engine first. Click one to see its stacks. With addons built by npm run valgrind:build-debug, our frames show file and line.
    •

Callgrind: CPU cost

    
How to read this
      
Callgrind counts the CPU instructions (Ir) a workload executes, running each workload's operation (one tick, one physics step, one cook…) many times.

      
    
        
  • Ir / op is instructions per operation. Unlike wall-clock time it barely changes between runs of the same code, so a change means the code, not the machine, changed.
    • 
        
  • Baseline is the committed reference in perf/callgrind-baseline.json. Change is the difference; beyond ±3% it is flagged.
    • 
        
  • A slower flag is a regression, or an intended cost that needs the baseline updated. Faster is an improvement. This includes the engine's own core cost: nothing is filtered out.
    • 
        
  • Counts are only comparable on the same Node version as the baseline. When the two differ the tab says so and colours everything amber instead of red or green.
    • 
        
  • Not measured means the latest run has no result for that workload, for example it was skipped or not run.
    •

History
Runs over time. Record one with npm run valgrind:record; add -- --promote to commit it to perf/history.json.

    
How to read this
      
    
        
  • Each point is one recorded run (a snapshot of memcheck and callgrind results at that moment, with the git commit it was taken at).
    • 
        
  • Committed runs live in perf/history.json and are shared through git. Local runs are only on this machine in valgrind-out/history.
    • 
        
  • The CPU chart shows each workload as a percentage of its first recorded value (100% = unchanged); a line climbing is a regression over time.
    • 
        
  • The memory chart shows error counts. A rising engine line is a new leak in our code.
    • 
        
  • Runs on different Node versions or with uncommitted changes (dirty) are marked, since they aren't strictly comparable.
    • 
        
  • Compare two runs shows what changed between any two: per-workload CPU cost, error counts, and which errors in our code appeared or went away.
