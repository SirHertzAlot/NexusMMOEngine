# What the engine can do

An honest inventory of what is in the box, what it costs, and where the
edges are. If you are deciding whether to build on this engine, read this
and then [Performance and constraints](PERFORMANCE.md); between them they should tell
you no as readily as yes.

Everything described here runs today from `npm start`. Where something is
partial, this page says so rather than rounding up.

---

## The one-paragraph version

Nexus is a **server-authoritative, data-oriented MMO engine** in TypeScript
on Node, with the numerically heavy work in C++ addons compiled into the same
process. One process simulates one region at a fixed 30 Hz over a
structure-of-arrays ECS; a browser client mirrors it and never decides
anything. The world it simulates is procedurally generated and baked offline:
terrain, biomes, settlements, roads, dungeons, loot and creature ecologies.
Gameplay systems arrive as **modules**, and the numbers they use are **data
files**, so a designer can change a game without touching engine code. It
scales by adding regions, coordinated by a world server that owns the durable
record.

---

## Simulation

| Capability | State |
|---|---|
| Fixed 30 Hz tick with a spiral-of-death guard | Built. Gaps over 250 ms are clamped, at most 5 catch-up steps per frame, the rest dropped and counted. A region that falls behind loses time and says so rather than compounding. |
| Structure-of-arrays ECS (bitECS), optionally SharedArrayBuffer-backed | Built. Component storage is typed arrays, so native kernels read it without copying. |
| Deterministic replay | Built and verified bit-for-bit over 500 ticks on 100 entities. Procgen is held to strict IEEE so bakes match across CPU vendors. |
| Three-thread data plane (gateway / sim worker / persistence worker over one SAB) | Built, **opt-in** (`MMO_DATA_PLANE=1`). Needs a durable ledger server; boot refuses to start without one. |
| Hot module reload of game systems | Built: the `reloader` system. |

The simulation step itself is cheap: 51,000 entities (1,000 players plus
50,000 NPCs) stepped at a p99 of 0.562 ms, 1.7% of the 33.3 ms budget. The
limit at high player counts is sending state, not computing it — see
[Performance and constraints](PERFORMANCE.md).

## Native C++ kernels

Ten N-API addons compiled into the server process. No IPC, no serialisation
at the boundary beyond typed arrays.

| Addon | What it gives you |
|---|---|
| `addon-physics` | Jolt: rigid bodies, character controllers, terrain height fields, ragdolls |
| `addon-navigation` | Recast/Detour: navmesh baking and pathfinding |
| `addon-procgen` | FastNoise2: deterministic terrain heightfields (SIMD) |
| `addon-terrain-kernel` | Tectonics and erosion over the heightfield |
| `addon-picg` | Cooks `.pcg` node graphs into procedural meshes; meshoptimizer |
| `addon-geometry` | Mesh and polygon Booleans (manifold, Clipper2) for bakes such as dungeon shells |
| `addon-scatter` | The scatter lattice, bit-identical to the JS reference |
| `addon-fanout` | Per-tick assembly of every session's delta envelope |
| `addon-integrate` | The native movement kernel of the data plane, and a benchmark kernel |
| `addon-perf-probe` | Instruction-count instrumentation for the valgrind harness |

`addon-template` is the skeleton to copy when you add your own. Writing a
native module is a documented path, not a fork: see
[Modules](MODULES.md#native-modules).

## World generation

All of it bakes **offline**, before the server starts, and none of it runs on
the tick.

- **Terrain.** A climate model drives it: tectonic uplift, erosion, rainfall,
  temperature and UV produce biomes rather than biomes being painted. The
  default spec is a 4 × 4 km island with a mountain spine and volcano,
  glaciers, a rain-shadow desert, rivers, lakes and 13 biomes, plus 6
  satellite islands. It bakes in under a minute.
- **Preview before you bake.** `npm run preview:world` draws the spec's
  biomes, rainfall, temperature and UV to a PNG in about 10 seconds.
- **Settlements.** Towns are sited from the survey, laid out, populated and
  baked to scene documents. Roads route between them, with guard outposts,
  inns, shacks, camp sites along the way and homesteads between.
- **Dungeons.** Generated by Wave Function Collapse over a graph, given a
  shell by CSG, furnished, and populated from species and rank tables.
- **Scatter and formations.** WFC decides what, a placement pass decides
  where, and a native scatter lattice distributes it.
- **Procedural assets.** PICG node graphs cook to meshes at bake time —
  trees and scenery that exist with no art pack at all.
- **Loot, ranks and recipes.** Composed at bake time from a rank ladder into
  pools the server reads.

`npm run bake:all` runs the whole chain in dependency order and skips steps
whose output exists. [World building](WORLD-BUILDING.md) and
[Procedural generation](PROCEDURAL-GENERATION.md) are the guides.

## Gameplay systems that ship

These are **real, running systems**, but they are also *a* game's systems.
The split now under way separates them from the engine core so you can keep,
replace or delete them (see [Building a game on this engine](BUILDING-A-GAME.md)). Treat
this list as what you get for free, not as what you are stuck with.

| Area | What is there |
|---|---|
| Movement | Walking, running, jumping, swimming, flying (permission-gated), stamina, character controllers against terrain and props |
| Combat | Weapon stances, 3-hit combos, guarding, dodge rolls, telegraphs, abilities, status effects, duels |
| Injury and death | Body-part damage, bleeding, bandaging and setting bones, death, corpses with ragdolls, respawn |
| Progression | Attributes, use-based skills, mastery, disciplines |
| Magic | Mana, spells, casting |
| Needs | Hunger and thirst |
| Creatures | Creature AI, crowd steering, needs-driven behaviour, spawn tables by species and biome, wild packs |
| Residents | Baked towns' people live out a day: schedules, jobs, movement |
| Items | Ground drops and pickup, bags, equipment, ground expiry, an item ledger |
| Economy | Gold wallets, player-to-player trade, NPC vendors, an auction house |
| Social | Region chat with per-channel range and rate limits, whispers, friends, blocks, parties, guilds |
| Quests | Quests and dialogue, place and bag conditions, quest logs |
| Dungeons | Instanced runs with party entry, a run HUD, results, and return to the world |
| Crafting | Materials, recipes, gathering nodes |

**Partial, and worth knowing before you plan around it:** the client has no
UI yet for player-to-player trade, the auction house, direct spell casting or
crafting — the server protocol supports all four, the windows are not built.
Armour and equipment are not finished.

## Networking

- **Interest management** is on by default. The world is cut into 64 m
  sectors; each tick the core encodes one delta per changed sector *once*,
  and a client's message is the concatenation of the sectors near it. Per
  client the cost is copying bytes, not encoding them.
- **Edge / core split.** `npm start` runs an edge process holding the
  players' sockets in front of the core. Authentication, rate limits and
  validation stay in the core. In the failure drills, a crash, restart or
  freeze on either side left no request hung.
- **Transports.** uWebSockets.js in production, `ws` as a pure-JS fallback.
  Note that if uWS has no prebuilt binary for your Node and OS, you silently
  get the slower path.
- **Wire format.** FlatBuffers for schema-evolving traffic from one source of
  truth (`packages/schema/mmo_engine.fbs`), plus a frozen-layout fast path
  for hot position and velocity deltas that encodes 16–20× faster and 3×
  smaller.
- **Slow and abusive clients** are handled by policy, not by hope: send
  suspension above a size limit with a fresh baseline on catch-up, token
  buckets on intents and pickups, and disconnect after repeated violations.

Every message is catalogued in [Message catalog](MESSAGE-CATALOG.md).

## Scaling out

Each region is its own process with its own 30 Hz loop and its own state. The
**world server is not optional** in this design: it is the durable store for
all game data, and it owns the registry, leases and hand-offs when a player
crosses a border. It never simulates, and player traffic never passes through
it.

Measured: 16 regions on one 4-core box (500 entities and 100 players each) at
a p99 region tick of 7.5 ms with every hand-off committing; roughly **4
regions per core** before ticks stretch past a frame. See
[The world server](WORLD-SERVER.md).

## Persistence

| Where | What |
|---|---|
| `region.db` (SQLite, WAL) | The region's hot cache: baked terrain, chunk entities, sessions, the item ledger. Full snapshot every 300 ticks |
| Per-domain SQLite files | Characters, economy, social, parties, guilds, quests, gathering, places, instances |
| World store (SurrealDB) | The system of record for world-level and cross-region records |
| Data-plane ledger (SurrealMX) | Durable writes from the persistence worker when the data plane is on |

Between snapshots, state that does not go through the ledger can be lost on a
crash — up to about 10 seconds of it. Check which of your state is ledgered
before relying on it.

## The editor

A standalone docking workspace, separate from the player client on purpose:
developer tools never ship in the game client. Workspaces cover world-scale
terrain sculpting, the scene viewport and ECS inspector, scene documents,
character records, gameplay rules and tables, dungeon and PICG graph tools,
live-ops telemetry, a database grid with an audit log, a story and quest
editor, the art pipeline, and a release pipeline with playtests. Play mode
runs a real server with the client's world view and the debugger's
performance graphs beside it.

See [The editor](EDITOR.md).

## Operations

Prometheus metrics for the edge, the channel and the core on one scrape
endpoint, with Grafana dashboards in the repository. Health endpoints,
structured logging through a lock-free ring to a dedicated worker that can
never slow the tick, runtime log-level changes, and documented failure
behaviour for every process. [Operations](OPERATIONS.md) has the whole
picture, including what the repository does *not* give you (backup tooling
and TLS termination are yours).

## What it is not

Being clear about this saves more time than any feature list.

- **Not a twitch engine.** Server-authoritative with interpolation and no
  prediction beyond the local walker. Input costs at least a round trip plus
  an interpolation tick before anyone else sees it.
- **Not able to put 1,000 players in one crowd yet.** The simulation can
  carry it; the end-to-end tick finishes about 43% of its ticks at that load.
  Plan on regions.
- **Not a general 3D engine.** The client is a mirror of an authoritative
  server. If you want a single-player or peer-to-peer game, nearly all of this
  is overhead.
- **Not licensed for release.** The repository is public and carries no
  licence, which means all rights reserved by default. You can read it, run it
  and learn from it; shipping a game on it is a capability being built, not a
  permission you have.
- **Not measured on dedicated hardware.** Every number in this repository
  came off shared machines. Trust the ratios; re-measure the absolutes.
