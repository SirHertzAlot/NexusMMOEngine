## What changed, and where (so the next person does not re-derive it)

Dungeon runs showed only a flat stand-in floor, then no props, then bright open-world
lighting. The fix follows the world's own path every time (data, ECS, reuse), with no
dungeon-specific client code for geometry:

- **Shell (#336).** `PcgAssetLibrary.addPrebaked` serves a baked `.shell.pcgm` like any
  asset; `DungeonInstance.mountShell` registers it as `dungeon:<id>`, spawns one static
  `Transform + AssetRef` entity at the origin and mounts the Pcg service
  (`mountPcgService`, extracted from `startPcgService`) on the instance's own gateway.
  The pool index names each shell. Client: the Pcg client follows the gateway the client
  joined (`MirrorClient.endpoint`), because after the hop it was asking the region with
  the instance's token (HTTP 401).
- **Props (#337).** `content/dungeons/props.json` is the world's spawn table keyed
  `dungeon:<kind>` (asset, collision box, `lift` for mounted kinds). The pool reads layout
  props, dressing furniture (with the bake's footprint) and torches; the instance builds
  each with `buildSpawn` + `spawnScatterEntity`. A kind with no entry is counted in
  `DungeonInstance.unspawnedProps`, not spawned (cracks, moss, debris, bones, icicles and
  roots wait for art, D4g). `DungeonWallSystem` skips static bodies (a solid prop at its own
  baked collider was pushed out of it). `packages/dungeon/test/props-table.test.ts` fails if
  the bake can place a kind the table does not name.
- **Look (#338).** `content/dungeons/looks.json` (per theme: palette, fog, hemisphere, dir,
  torch; shared `emitters` and `maxLights`) is validated by the server and sent once on
  entering as a `look` dungeon message. Client `render/dungeon-look.ts` (`DungeonAmbience`)
  hides the sky, clouds, rain and sea, sets fog and dim lights, eases a budgeted pool of
  point lights onto the nearest torches and braziers, and restores everything when the run
  ends. The shell draws as one group per material slot (`pcg-meshes.ts`, the worker payload
  carries `triangleMaterial`), each slot a matte flat-shaded material from the palette.

Two bugs worth knowing, both found by checking in the running client rather than by unit
tests: component stores are process-wide typed arrays and bitECS recycles entity slots, so
a freshly spawned entity inherits a dead entity's position unless **every** field is
written (the shell was drawn 128 m away); and the wall system moves any `Transform +
Velocity` body, which includes static props.

## The rebake

```
node packages/dungeon/dist/src/cli.js --n 30 --fresh --out <repo>\packages\engine-core\data\dungeons
```

30 dungeons (4 ancient, 8 molten, 6 verdant, 6 grim, 6 frost; ranks 1 to 5), every one with a

torches and 1,115 resource veins in total. The previous pool is kept at

the backup to `dungeons`. A rebake needs no code from these PRs, but only the PR branches
draw the result.

## How to playtest

The PRs are not on `main`, so run the branch. The main checkout may be on another branch with
uncommitted work, so use the worktree (`git worktree list` shows it) rather than switching it:

```powershell
cd C:\Users\user\Downloads\mmo-dungeon-shell          # branch feat/dungeon-look (or docs/handoff-2026-10-20)
$env:MMO_DATA_DIR = "C:\Users\user\Downloads\mmo-engine-full\packages\engine-core\data"   # your world and the rebaked pool
npm start -- --dev                                    # stop your own servers first: it uses ports 7777, 3000, 3001, 5391
```

Checked up to the port bind: from the worktree with that data folder it builds, loads the 30-layout
pool and starts the core, and it stopped there only because another server already held port 7777.
It was not run all the way through, so if the client does not come up, that is the first place to look.

Art: the dev server serves `<repo>\assets` (the licensed art, git-ignored, never copied or
committed). The worktree has none, so characters and models draw as stand-ins. To see the art,
point a directory junction at it (a pointer, not a copy; `/assets/` is ignored by git):
`cmd /c mklink /J assets C:\Users\user\Downloads\mmo-engine-full\assets`.

To enter a dungeon: the barrow gate is at world (530, 600), radius 8 (`content/dungeons/entrances.json`);
spawn is (448, 560). Walk to the gate and press E. Each entry draws a dungeon from the pool by
rank and theme, so enter a few times to see all five themes. If the settlement near the gate
makes it hard to reach, raise `radius` there temporarily (and put it back).

What to look at: walls, ceiling and floor of the shell; the standing props (stand-in boxes until
the art catalog names `dungeon:<kind>` models); torchlight in each theme's colour on matte
stone with fog and no sky; the HUD timer and the open-chests button.

## Known issues and things that bite

- **`npm start` and `npm ci`.** `scripts/start.mjs` runs `npm ci` whenever the lockfile changed.
  `npm ci` deletes `node_modules` first, so on Windows any locked file (a running dev server,
  esbuild, an addon) fails it with EPERM partway and leaves a broken tree (missing `typescript`,
  `flatbuffers`, `express`, ...). Stop servers first; repair with `npm install --ignore-scripts`
  and restore the root lockfile's `"packages": {"dev": true, "optional": true, "peer": true}`
  block. A safer `start.mjs` is a worthwhile small PR.
- **The look is untuned.** Palette and torch numbers are a first pass; frost was blown out once
  (its torch colour is pale and bright), so torch strength is per theme (50 to 80 candela).
  Tuning was deferred on request.
- **Every enemy is a goblin.** `content/rules/creatures.json` has one creature; the instance falls
  back to it for any baked species (fiend, imp, elemental shard, ogre, ...). The species roster
  (`packages/species`) has tier, pack and body; deriving creatures from it is the planned fix.
- **Stale compiled tests.** `dist` is git-ignored and never cleaned, so a deleted test's compiled
  file still runs under `node --test dist/test/**` and fails. Delete the orphaned file.
- **Flaky under load.** The `engine-core` regional re-bake test (a SurrealDB `rocksdb ... timed out`)
  and the persistence query-timeout test fail in a full run on a busy machine and pass alone.
- **Pre-existing failures on `main`:** `build` (`deployLocal`, `collectInputFiles`) and `editor`
  (`buildCatalog`) tests fail identically without these changes.
- **Remote branch to delete:** `git push NexusMMORepo --delete fix/build-deps` (merged in #324).
- **A merge by the assistant was blocked** by the harness's auto-mode check once; merging is the
  owner's.

## What is queued, in the order asked

1. **EM1 enemy models from data.** A data file maps each enemy kind to a local art model, with the
   stand-in block as the dev fallback when the model is absent. Enemies derive from the species
   roster: strength comes from size and composition (small species weakest; trolls, ogres, golems
   and megafauna much stronger; bears and mega-ursas on par with them; demons the apex, smarter,
   with complex magic and attack rhythms that overwhelm and torture), scaled against the player's
   average stats and then debuffed and capped to something players can realistically beat.
2. **LS1 loading screen.** The client waits for models (PCG meshes, art models, the character kit)
   to populate before revealing the world; first load each time is slow and shows stand-ins popping in.
3. **RN1 dungeon resource nodes.** Spawn the baked veins (`dressing.resources`: kind, tier, position,
   wall facing, room; 1,115 in the current pool) through the world's `ResourceNode` registry
   (scene-spawn `deps.resources.register`; the client already handles `client.resources` and
   `gather`), switchable on or off in `content/dungeons/instances.json`.
4. D4f chests, traps and the boss crystal as world entities (the run's chests are HUD-only logic
   today); D4g decals once there is art.

## How the work was verified (to repeat it)

Unit tests per workspace (`npm test --workspace=@mmo-engine/<name>`) plus a real client check:
copy the data folder to a scratch folder, run the core on spare ports
(`MMO_PORT`, `CORE_CHANNEL_PORT`) with `MMO_SPAWN_OVERRIDE=525,600` and the entrance radius
temporarily widened, run the client (`npm run dev --workspace=@mmo-engine/client -- --port 5392
--strictPort`), and drive it with Playwright (Chromium) through create account, create character,
press E at the gate. Capture three.js scenes through `window.__THREE_DEVTOOLS__` to list the
instanced prop meshes. Revert the radius afterwards and stop only the processes on those ports.
