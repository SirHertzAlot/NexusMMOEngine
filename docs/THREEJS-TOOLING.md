# Three.js Tooling: Findings and Build Order

**Compiled:** 2026-10-10. A decision-free execution spec.
**Sources folded in:** `THREEJS-TOOLING-REVIEW.md` (2026-10-09), `THREEJS-DIRECTORY-REVIEW.md` (2026-10-09, 371 listings / 30 categories), `TOOLING-INTEGRATION-PLAN.md` (2026-10-09), animouse deep review (2026-10-10), `ANIMATION-RUNTIME.md` (2026-10-06).
**Stack facts:** R3F 9 mirror client (`apps/client`), vanilla-three.js editor (`apps/editor`), art bake pipeline (`packages/art`, Zod-validated manifest), server-authoritative (the server decides animation clips; the client renders bones). Permissive-only licenses. Every technique needs a cost/benefit gate. The developer machine is Windows, Node 25.

The roadmap tracks status in [section 1e](ROADMAP.md#1e-tooling-and-asset-performance); this page is the spec behind it.

## How to read this doc

- **ADOPT** = integrate now, in the build order below. The verdict is locked; execution is TDD with gates.
- **EVALUATE** = spike first, then decide. Each has a concrete spike definition and a pass/fail bar. Do not adopt on the directory card alone.
- **PARK** = do not touch. The reason is recorded; revisit only when the stated condition changes.
- **BOOKMARK** = manual reference, no integration.

## ADOPT: build order

Execute in this order. Each phase ends with a gate; no phase starts until the previous gate is green. Pin every version in Phase 0; never float on `latest`. Numbers go in the manifest: if it isn't measured, it didn't happen.

### Phase 0: pin versions, record baselines (no behavior change)

1. Pin: gltfpack binary (latest stable meshoptimizer release at execution time), `@gltf-transform/cli` npm, `gltfjsx` npm, `leva` npm, `lil-gui` npm, `animouse` npm (0.8.0 verified 2026-10-10; re-check latest at execution). Record all in `packages/art/README` and in this doc's appendix.
2. Pick 3 baseline assets: one prop, one character-ish mesh, one baked vista/environment piece from the current corpus.
3. Per asset record: file bytes, client load time (ms, median of 5), rendered screenshot hash. Check into test fixtures.
4. Windows check: `gltfpack -h` runs, `npx gltfjsx --version` runs, `npx @gltf-transform/cli --version` runs **including a trial KTX2 conversion**. The KTX2 codec path is the most likely Windows difference; prove it in Phase 0.

**Gate:** versions pinned and recorded; 3 baselines checked in; KTX2 trial green on Windows.

### Phase 1: compression pipeline (bake) and decoders (client)

Division of labor, locked: **gltfpack owns geometry, gltf-transform owns textures and scene cleanup.**

**1a. Client decoder first** (so compressed assets always load):

- Wire `MeshoptDecoder` into the client's GLTF loading path (AssetProvider / client loader setup); serve its `.wasm` from client static assets.
- Wire three.js `KTX2Loader` and the Basis Universal transcoder wasm into the texture loading path.
- Test each against existing *uncompressed* assets: decoder present but idle, zero behavior change, existing tests green.

**1b. gltfpack encode (bake):**

- Add a `compress` step to `packages/art` (next to `src/convert/`): shell out to the pinned gltfpack binary with meshopt compression (`-cc`). v1 does NOT touch textures (that's 1c's job, a deliberate scope cut).
- Extend the Zod manifest (`packages/art/src/manifest.ts`): `compression: "meshopt"`, `rawBytes`, `compressedBytes`. The binary path is config (env var / config file), never hardcoded.

**1c. gltf-transform texture and cleanup (bake):** runs on the gltfpack output.

1. `prune` + `dedup`: always safe, always on.
2. Texture conversion per slot (locked v1 default; tunable in config, not code): baseColor to WebP; normal, occlusion, metallicRoughness to UASTC KTX2. Full ETC1S KTX2 is a named follow-up after the KTX2 eval gate, not this phase.
3. Texture resize caps per quality tier (config).
4. Extend the manifest: `textureCompression` (per slot), `textureBytes` before/after, `cleanupRemoved` counts.

**1d. Golden test:** the 3 baseline assets raw, then gltfpack, then gltf-transform, then load in client, then render. Assert the screenshot hash matches Phase 0 (zero visual delta) and the manifest shows `compressedBytes < rawBytes`.

**Gate:** at least 40% byte reduction on the sample (or a written reason per asset), zero visual delta, both decoders live in the client, manifest schema extended, tests green.

### Phase 2: gltfjsx component workflow

1. `gltfjsx` as a devDependency of `apps/client`.
2. Convention (locked): `npm run models:generate -- <baked-compressed.glb>` writes `apps/client/src/models/generated/<Name>.tsx`, committed, with a `// @generated by gltfjsx — do not hand-edit` header. Regenerate, don't patch. One component per asset; prop names follow existing client conventions.
3. Document in `apps/client/README.md`: bake, gltfpack, gltfjsx, import. Regeneration rule: baked GLB changes mean regenerate (manual in v1; a stale-check script is a named follow-up).
4. Wire one model end-to-end into a dev scene.

**Gate:** one asset through the full chain, pixel-identical to the pre-component render.

### Phase 3: dev tweak overlays (Leva and lil-gui)

1. `leva` as a **devDependency** of `apps/client`, mounted behind `import.meta.env.DEV`, impossible to render in production by construction. Seed 3 control groups: quality-tier override, post-processing master toggle and intensity, key light intensity and direction.
2. `lil-gui` as a devDependency of `apps/editor` (vanilla three.js; Leva is React-first and doesn't fit). Same DEV-gate discipline.
3. Prod-bundle check (automated, not eyeballed): the production build contains zero `leva` / `lil-gui` bytes.

**Gate:** panels work in dev, controls drive the scene, production bundles clean.

### Phase 4: placeholder assets (Gobkit)

- Pull the CC0 rigged/animated low-poly GLBs via the no-auth JSON manifest at `/api/free`. Land them in the prototype asset library as animation-pipeline test subjects (retargeting, crowd systems). These are placeholders, never shipped art.

**Gate:** at least 3 characters load in the client, play their clips, and survive the Phase 1 compression pipeline.

## EVALUATE: spike definitions

Each spike is time-boxed. Pass = meets the bar below; fail = write the reason and park it.

### animouse: animation state machine with blend trees (spike first, high value)

- **What:** MIT (verified 2026-10-10 against jango-git/animouse). TypeScript. 95 commits, created 2025-05. npm 0.8.0. Peer dep three.js ^0.175.0. Event system via `eventail`.
- **API:** `ClipState` (single clip + lifecycle events), `LinearBlendTree` (1D: idle, walk, run on speed), `PolarBlendTree` (2D polar: direction + intensity), `FreeformBlendTree` (2D Delaunay triangulation), `AnimationMachine` with event-driven / automatic (on-complete) / data-driven (condition) transitions, configurable crossfade durations, and **time events** (fire callbacks at clip fractions: footstep sounds at 0.25/0.75, attack impact at 0.6).
- **Why it matters to us:** our client animator (`character-animator.ts`) is hand-rolled two-layer base/action with crossfading. animouse is the locomotion-blending layer we don't have, and its time events are the hook for footstep audio (EA24) and hit-frame feedback. It sits on `THREE.AnimationMixer`, which we already use. It does NOT conflict with the server-authoritative contract: the server still decides `(clipId, startTick, rate, layerMask)` (EA21); animouse is purely the client's blending/execution layer.
- **Risks:** 1 star, 1 watcher, 0 forks: bus factor 1, single author. Mitigation: it's small (a few hundred lines of state-machine logic over the mixer), MIT means we can vendor/fork if the author vanishes. The math (Delaunay triangulation for freeform) is standard.
- **Spike:** wire animouse into a dev scene with 3 Gobkit characters: `LinearBlendTree` for locomotion (idle/walk/run on speed), `ClipState` for one attack with a time event firing a console log at the hit frame. Measure: blend correctness (no popping), per-frame CPU cost at 60 fps, and time-event timing accuracy vs the clip's actual duration.
- **Pass bar:** blends are pop-free, time events fire within ±1 frame of the expected clip fraction, per-character overhead under 0.1 ms/frame, and the code reads clean enough to vendor if needed.

### NixieFX: visual VFX editor and runtime

- **What:** local-first visual particle editor and runtime for three.js. The directory states an MIT runtime; **editor license unverified. Verify before any commitment.**
- **Why:** it's the visual editor three.quarks lacks. Our VFX authoring is code-only today.
- **Spike:** build one production-grade effect (e.g. a sword-hit burst) in the editor, export, run in the client. Measure CPU cost with the same methodology as the planned three.quarks measurement. Compare authoring time vs hand-coding the same effect.
- **Pass bar:** editor license confirmed permissive, runtime CPU within 10% of the hand-coded equivalent, authoring at least 2x faster.

### EZ-Tree: procedural trees

- **What:** MIT (verified via multiple sources). Library (`@dgreenheck/ez-tree`) and web app; exports GLB and PNG sprites. Same author as three-pinata (David Greenheck), already trusted in our stack.
- **Why:** feeds the octahedral-impostor baker directly: procedural species in, baked atlases out. Deterministic seeds make it bake-pipeline friendly.
- **Spike:** generate 3 species with distinct silhouettes, bake to impostors, measure bake time and atlas bytes.
- **Pass bar:** species are visually distinct at impostor distance, and the bake is deterministic (same seed gives byte-identical output).

### InstancedMesh2: BVH-culled scattering

- **What:** MIT per research. InstancedMesh + BVH frustum culling + LOD; reportedly 200k trees.
- **Why:** the scattering-side complement to EZ-Tree, our forest rendering path.
- **Spike:** scatter 50k EZ-Tree instances, measure draw calls and frame time vs naive InstancedMesh.
- **Pass bar:** single-digit draw calls for the forest, frame time within budget at 60 fps on target hardware.

### GLB Delivery Desk: batch GLB QA

- **What:** batch GLB inventory/handoff reports (file, geometry, image, material checks). License to verify.
- **Why:** ready-made QA gates adjacent to our manifest validation.
- **Spike:** run against 10 baked assets; diff its checks against our manifest validators.
- **Pass bar:** adopt the *missing checks as validators* rather than the tool, unless it covers over 50% of our validation surface with zero overlap.

### Meshamorphosis: batch FBX to GLB and Mixamo batching

- **What:** batch-converts FBX/OBJ/glTF to GLB; can batch-add Mixamo animation FBX files. License to verify.
- **Why:** our animation pipeline retargets from GLB clip sources; Mixamo is the standard free source. Batch ingest slots into the bake's animation stage.
- **Spike:** batch-convert 5 Mixamo FBX clips to GLB, retarget one onto a Gobkit character in the client.
- **Pass bar:** license confirmed permissive, clips retarget without manual bone remapping.

### lygia: modular GLSL functions

- **What:** granular GLSL shader functions by patriciogonzalezvivo. MIT (verify on adoption).
- **Why:** a function-level library for the shader R&D experiments: import math, not frameworks. Fits the "reimplement, don't vendor" posture at the smallest unit.
- **Spike:** use 3 functions in one shader experiment; confirm no build-system friction.
- **Pass bar:** zero integration cost, functions are genuinely reusable across experiments.

## PARK: do not touch

| Tool | Reason | Revisit when |
| --- | --- | --- |
| Theatre.js | `@theatre/studio` (the visual editor, the whole point) is **AGPL-3.0**, which trips permissive-only. Plus ownership churn (`@tomorrowevening/*` forks). | A cinematics need exists AND the AGPL question is answered |
| Needle Inspector | License unverified | License confirmed permissive |
| Three.js DevTools | Same license-check gate as Needle | With Needle Inspector |
| TSL editors (TSL Graph, Nodetoy, tsl-textures) | Tied to the TSL/WebGPU path | WebGPU decision made |
| GSAP 4 | Not a 3D-engine concern; candidacy is editor/HUD tweens only | Feature list public and a concrete tween need |
| AI 3D generators (Rodin, Tripo, Meshy, etc.) | Art is supplied input; style risk and murky training-data licensing | Never without a license and style review |

## BOOKMARK: manual reference, no integration

- **gltf.report** (donmccurdy): web GLB diagnostic, supports BASIS/KTX2. Manual QA companion to the bake.
- **Kenney / Quaternius** (CC0): placeholder assets: nature, medieval, animated characters.
- **Polyhaven / AmbientCG** (CC0/free): HDRIs and PBR textures for lighting/material prototyping.
- **Mixamo** (free): character models and animations; the standard free clip source for the animation pipeline.
- **VAT Blender addon**: vertex-animation-texture generation; a research note for the crowd-animation problem, not a tool.

## Already decided (not re-litigated here)

- **ozz-animation**: ADOPT (MIT): bake pipeline (N-API) and native side. From `ANIMATION-RUNTIME.md`.
- **acl**: ADOPT at bake (MIT): clip compression. From `ANIMATION-RUNTIME.md`.
- **Motion matching**: PARKED: 0.5 GB+ memory, no mocap corpus, unmeasured per-character CPU. The hybrid state machine is the path, which is exactly what animouse provides on the client.
- **Server/client animation split** (locked): the server sends `(clipId, startTick, rate, layerMask)`; the client renders bones; hit detection never from bones. animouse lives strictly on the client side of this line.
